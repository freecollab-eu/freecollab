# Customer cloud file picker

The optional `CLOUD_FILES_ENABLED=true` feature adds deliberate cloud file selection to channel files. It is off by default. Google Drive and OneDrive reuse an existing customer OAuth **files** connection for this exact workspace and channel (`SYNC_ENABLED=true` is also required). Dropbox and Box have separate customer OAuth application connections. FreeCollab does not supply provider credentials or obtain consent automatically.

Native channel administrators who are also current workspace administrators can browse the granted collection, navigate its subfolders, select one exact revision, and confirm importing it. The result is a normal immutable `File` blob, `FileDocument` and `FileVersion`, visible through existing channel file permissions and downloads. A file owner can explicitly import a new version by supplying the current document version. The picker performs no provider writes and does not enable background synchronization. The imported copy follows normal channel policies: if this channel already has an enabled sync connection, its existing worker can later synchronize the new copy under that previously approved grant. Channel Files shows the existing external-sharing notice; importing is not an exemption from those channel rules. Google native documents, sheets and slides use the existing PDF export behavior.

The picker only issues read operations. Existing Google/Microsoft sync tokens retain the scopes explicitly approved for sync; their broader write authority is not reduced by opening the picker. Dropbox requests `files.metadata.read files.content.read`. Box application permissions are configured by the customer in Box. Use the displayed exact callback URL when registering the application; Box requires its customer client secret. Dropbox root is a path (empty selects the app's visible root), Box root is a numeric folder ID, Google root is a folder ID, and OneDrive requires customer tenant, drive and folder IDs. Native password and MFA/recovery confirmation protect creation, replacement consent and disconnect. Starting consent clears old account tokens before redirecting.

## Encrypted channels

Encrypted and preparing channels do **not** support server browsing, provider downloads or server import. The UI calls this mode **Encrypted provider links only**, not a full encrypted cloud picker. A person selects a file in their provider, pastes its HTTPS sharing link and acknowledges that the provider still controls access and sees external visits. The client requires a verified current encryption device and normal verified recipients, then sends an encrypted `eu.freecollab.cloud-file` event. The server verifies the encrypted event belongs to the current sender and channel and stores only its opaque event reference. The client checks room, sender, event type, ID, workspace, channel and revision before showing any decrypted URL or title. A failed secure binding never falls back to plaintext.

The link does not grant provider permission and FreeCollab never fetches it automatically. Links open only after a click with `noopener noreferrer` and no referrer. Native link metadata is encrypted with the existing channel message key ring; the native server can decrypt it. Both modes deliberately distinguish provider access from channel membership. To import bytes into an encrypted channel, download them yourself from the provider and use the existing local file upload, which encrypts on the trusted client. No server-side plaintext proxy is provided.

## Request and transport boundaries

All routes are under `/workspaces/{workspace_id}/channels/{channel_id}/cloud-files`, apart from `/cloud-files/oauth/callback`. The installation's normal `/api` reverse proxy prefix applies. The API offers connection listing, Dropbox/Box application creation, explicit OAuth start/disconnect, bounded browse pages, selected-file import, and bounded link listing/create/removal. It never returns OAuth credentials.

* Every browse and import checks the current native actor, unrestricted session, workspace/channel administration, original active grant administrator, selected workspace mapping, direct-message constraints, and absence of any secure-channel binding. The same checks run after provider I/O under workspace/channel locks before metadata or bytes become visible. Consent revision changes, logout, blocking, membership removal and enabling encryption discard the response.
* Provider calls use fixed API endpoints and the existing public-HTTPS DNS-pinned transport with certificate hostname verification, platform proxy policy, response limits and operation deadlines. No redirect is followed by default. One explicit transport option returns a bounded single `Location` for 302/303 without following it or reading its body. Only the Box content adapter uses it, permits HTTPS `*.boxcloud.com` with no URL credentials or nonstandard port, and follows once without an Authorization header. Redirects from that CDN are refused. OneDrive uses the existing constrained preauthorized content-host logic, also without Bearer forwarding.
* Folder traversal is bounded to 16 ancestors for Google/Microsoft and requires the selected root; Dropbox validates normalized paths within the root and exact parent; Box validates provider ancestry and exact parent. Page tokens are sealed to connection, consent revision, folder and a ten-minute expiry. Lists contain at most 100 entries per provider page; the UI loads at most 1,000 entries per folder.
* Browse and import require the exact displayed `connection_revision`; page and selectable-entry responses bind both connection ID and consent revision. A same-ID replacement account/configuration is rejected before provider I/O, even when its file IDs and ETags collide. Explicit Reload connections clears the old selection. Selection also includes an exact provider ETag/revision. Metadata, collection ancestry and revision are checked before and after downloading; a changed or moved item returns a conflict. Downloads and imports are capped at 50 MiB and the existing upload MIME allowlist. Provider errors are sanitized and never include provider bodies or secret values. Browse/import rate limits run before any write locks.
* A per-user request ID binds a fingerprint of the connection, exact selection and destination to the acknowledged immutable file. Retries return the same file. Reuse for another selection returns 409. Erasure preserves an import tombstone with `file_id=NULL`; replay returns 410 and cannot resurrect bytes.
* Customer secrets, refresh/access tokens, and PKCE verifiers are sealed with the account-security key. OAuth attempts bind state, browser cookie, current native session digest/auth version and consent revision. Attempts are one-use, expire after ten minutes, and recheck authority after token exchange. No credential is stored in browser storage or query parameters. A refresh is retried once and saved only into the unchanged authorized connection.

## Persistence and integration

`cloudfileconnection` stores Dropbox/Box configuration and sealed credentials. `cloudfileoauthattempt` stores one-use hashed OAuth state and sealed verifier. `cloudfileimport` stores idempotency receipts (`file_id` is nullable for erasure). `cloudfilelink` stores server-encrypted native fields or opaque Matrix references. Existing Google/Microsoft credentials stay in `remotesyncconnection`. Imported byte storage and file versions use the normal file tables and cleanup paths. Native cloud-link history participates in the encryption migration fence; retention/ordinary file deletion preserve import tombstones.

The parent dialog renders `CloudFilesPicker({workspaceId, channelId, onImported?, onClose?})`. It uses existing appearance CSS variables, translated Swedish/English source strings, explicit confirmation controls and account/generation guards. All routes are private/no-store. Customer SSO tokens can use membership-scoped provider links, but cannot operate the native credential picker.

## Verification

`backend/tests/test_cloud_files.py` covers import/version/retry semantics, tombstones, revocation during provider I/O, private channel/workspace/SSO restrictions, OAuth callback/browser/session/revision races and encrypted pointer fences. `backend/tests/test_cloud_file_providers.py` exercises **actual verified HTTPS** to four private provider fixtures through the unchanged DNS-pinned connection and proxy path, including bytes, content redirects, ETag races, root escape and provider revocation. No real provider is contacted. `frontend/tests/cloud-files.test.mjs` checks verified-device enforcement, opaque encrypted requests, tampered Matrix events, URL validation and auth races. `frontend/tests/cloud-files-browser.py` uses Chromium, a live isolated API and the four private HTTPS fixtures for browse/select/confirm/import with exact bytes, version creation, external links, Swedish labels and a 320px viewport.

The private fixtures verify FreeCollab's protocol and security behavior. A customer must still register its own production applications, approve its own provider consent, and check its organization's provider policies. No external account was connected by these tests.
